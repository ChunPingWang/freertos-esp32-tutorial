# 第 8 章：總結比較 —— 實測兩種架構

前面各章分別體驗了兩種架構。本章把**同一個應用**用兩種方式各寫一次，以相同的方法量測，用數字回答「差在哪裡」。

- 超級迴圈版：[`examples/08_compare_superloop/main/main.c`](../examples/08_compare_superloop/main/main.c)
- FreeRTOS 版：[`examples/09_compare_rtos/main/main.c`](../examples/09_compare_rtos/main/main.c)

## 應用規格

| 工作 | 規格 |
|---|---|
| LED | 每 100 ms 切換一次 |
| 重運算 | 每 1 秒執行一次，每次佔用 CPU 200 ms（模擬濾波、加密、畫面更新） |
| 按鈕 | 按下時記錄事件 |
| 報告 | 每 5 秒印出統計 |

## 量測指標

| 指標 | 定義 | 意義 |
|---|---|---|
| **LED 週期誤差** | 相鄰兩次切換的實際間隔與 100 ms 的差距，取 5 秒內的最大值 | 週期性工作的準確度（jitter） |
| **按鈕延遲** | 從 GPIO 中斷發生（按下的瞬間）到主程式／任務開始處理的時間 | 事件的反應時間 |

兩個版本都由 ISR 記錄按下瞬間的時間戳記，確保量測基準一致。

## 公平性

為了確定差異來自「架構」而不是其他因素：

- 兩個版本的按鈕都使用 GPIO 中斷。超級迴圈版是實務上最佳的寫法（前景／背景架構：ISR 設旗標、主迴圈檢查），不是刻意寫差的版本。
- 超級迴圈的各個 job 都是非阻塞的狀態機寫法。
- FreeRTOS 版的所有任務都綁在核心 0，與超級迴圈的主迴圈相同，沒有多用一顆核心。
- 重運算的內容與時間長度相同。

## 兩份程式的結構對照

**超級迴圈版**

```c
while (1) {
    led_job();       // 時間到了嗎？到了就切換
    heavy_job();     // 時間到了嗎？到了就運算 200 ms ← 這裡會卡住所有人
    button_job();    // 旗標被 ISR 設起來了嗎？
    report_job();    // 時間到了嗎？到了就列印
}
```

**FreeRTOS 版**

```c
button_task (優先權 4)：xQueueReceive(...)        → 處理
led_task    (優先權 3)：vTaskDelayUntil(100 ms)   → 切換
report_task (優先權 2)：vTaskDelay(5000 ms)       → 列印
heavy_task  (優先權 1)：運算 200 ms → vTaskDelayUntil(1000 ms)
```

## 實驗步驟

### 1. 超級迴圈版

```bash
cd examples/08_compare_superloop
idf.py set-target esp32
idf.py -p <你的序列埠> flash monitor
```

- 先不按按鈕，記錄 3 筆報告中的 `LED error max` 與 `loop max`。
- 接著**持續隨機地按按鈕約 30 次**（間隔至少半秒），記錄 `latency max`，以及觀察 `latency last` 的變化範圍。

### 2. FreeRTOS 版

```bash
cd ../09_compare_rtos
idf.py set-target esp32
idf.py -p <你的序列埠> flash monitor
```

以相同方式操作並記錄。

> 按鈕延遲是否落在重運算期間是機率問題：每秒有 200 ms 在運算，所以隨機按下時約有 20% 的機率遇上。
> 按的次數越多，越能觀察到最壞情況。

## 預期結果

以下是依程式結構推導的預期，**不是實測值**：

| 指標 | 超級迴圈（預期） | FreeRTOS（預期） | 推導依據 |
|---|---|---|---|
| LED 週期誤差最大值 | 約 100,000～200,000 us | 遠小於 1,000 us | 超級迴圈：LED 會被 200 ms 的運算卡住。RTOS：`led_task` 優先權高於 `heavy_task`，準時被喚醒 |
| 按鈕延遲（運算以外的時間按下） | 數微秒～數十微秒 | 數十微秒 | 超級迴圈空轉時每圈極快；RTOS 需一次上下文切換 |
| 按鈕延遲最大值 | 接近 200,000 us | 數十微秒，偶爾稍高 | 超級迴圈：運算期間按下，要等運算結束。RTOS：`button_task` 可搶佔任何任務 |
| 迴圈最長時間 | 約 200,000 us 以上 | 不適用 | 即 200 ms 的運算加上列印時間 |

值得注意的一點：**在系統空閒時，超級迴圈的反應可能比 RTOS 還快**——它不需要上下文切換。
兩者的差別不在「平均」，而在「最壞情況」：

- 超級迴圈：最壞情況由**最慢的那件工作**決定。
- RTOS：最壞情況由**比你優先權高的工作**決定，與低優先權的工作無關。

對即時系統而言，重要的正是最壞情況。

## 延伸實驗

1. **加重負載**：把兩個版本的 `HEAVY_WORK_MS` 都改成 `500`。預期：超級迴圈的兩項指標惡化到約 500 ms；FreeRTOS 版幾乎不變。
2. **新增一件工作**：假設要再加一個「每 10 ms 取樣一次」的工作。
   - 超級迴圈：新增一個 job 很容易，但它同樣會被 200 ms 的運算卡住。要達到規格，必須回頭改寫 `heavy_job`，把它拆成每段小於 10 ms 的片段。
   - FreeRTOS：新增一個優先權高於 `heavy_task` 的任務即可，既有程式不需要更動。
3. **比較資源用量**：分別在兩個專案目錄執行 `idf.py size`，比較映像檔大小。由於 ESP-IDF 中 FreeRTOS 無論如何都會被連結進來，兩者的差異預期很小；RAM 的主要差異在於 FreeRTOS 版多了四個任務的堆疊（4 × 4096 bytes）。

## 程式碼層面的比較

數字之外，也請比較兩份原始碼本身：

| 觀察點 | 超級迴圈版 | FreeRTOS 版 |
|---|---|---|
| 週期控制 | 每個 job 自己保存時間戳記並比較 | `vTaskDelayUntil` 一行 |
| 等待按鈕事件 | 每圈檢查旗標 | `xQueueReceive` 阻塞等待 |
| ISR 與主程式的資料交換 | 共用的 `volatile` 變數，需自行確保讀寫安全 | 佇列，由核心保證安全 |
| 工作之間的相依性 | `heavy_job` 的執行時間影響所有 job | 各任務只受較高優先權的任務影響 |
| 統計變數的存取 | 單一執行路徑，不需考慮 | 多個任務存取，需要思考是否安全 |
| 需要事先決定的事 | job 的順序 | 每個任務的優先權與堆疊大小 |

最後兩列是 RTOS 版本多出來的負擔。範例 09 的統計變數之所以可以不加鎖，是因為每個變數只有一個任務會寫入，且都是 32 位元（讀寫各是單一指令）。這類判斷在超級迴圈中完全不需要做。

## 結論

| | 超級迴圈 | FreeRTOS |
|---|---|---|
| 最壞反應時間 | 取決於最慢的工作 | 取決於優先權，可以設計 |
| 週期性工作的準確度 | 受其他工作影響 | 高優先權任務不受低優先權影響 |
| 加入耗時工作 | 需要拆解成狀態機 | 放進低優先權任務 |
| 擴充性 | 每次新增工作都要重新檢視整體時序 | 新增任務，影響範圍有限 |
| 並行問題 | 幾乎沒有 | 必須處理 |
| 資源用量 | 最少 | 每個任務需要堆疊 |
| 適合 | 小型、工作短、時序單純的系統 | 有耗時工作又需要即時反應、會持續擴充的系統 |

**RTOS 並沒有讓 CPU 變快**。兩個版本中，200 ms 的運算都確實花了 200 ms。
RTOS 做的是讓你能夠**指定什麼比較重要**，並保證重要的事不會被不重要的事耽誤。
交換條件是：你必須開始思考並行、優先權與堆疊。
