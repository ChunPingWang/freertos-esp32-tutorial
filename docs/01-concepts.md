# 第 1 章：超級迴圈 vs RTOS —— 核心概念

本章不寫程式，先把兩種架構的原理講清楚。後面每一章的實驗，都是在驗證這裡的說法。

## 問題：一顆 CPU，多件事情

嵌入式系統幾乎都要「同時」做好幾件事。以本教程的實驗為例：

1. 讓 LED 規律閃爍
2. 定期讀取感測器並做運算
3. 使用者按下按鈕時立刻反應

CPU 一次只能執行一道指令，「同時」其實是快速地輪流。**由誰決定輪到誰、什麼時候換手**，就是兩種架構的根本差異。

## 超級迴圈（superloop）

### 結構

```c
int main(void)
{
    init();
    while (1) {
        task_led();
        task_sensor();
        task_button();
    }
}
```

所有工作排成一列，依序執行，做完一輪再從頭開始。**由程式設計師在寫程式時決定順序**，而且每件工作必須「自願返回」，下一件才有機會執行。這種方式稱為**合作式（cooperative）**排程。

### 前景／背景架構

實務上的超級迴圈通常會搭配中斷：

```
背景 (主迴圈)：   led → sensor → button → led → sensor → ...
前景 (中斷)  ：        ↑ 按鈕中斷：只設一個旗標就返回
```

中斷服務程式（ISR）只做最緊急的小事（例如設旗標、收一個位元組），真正的處理留給主迴圈。這仍然是超級迴圈——因為「處理」要等主迴圈輪到才會發生。

### 關鍵特性

> **任何一件工作的反應時間，最壞情況 = 其他所有工作執行時間的總和。**

如果讀感測器要 300 ms，按鈕的反應最慢就會延遲 300 ms 以上，不管按鈕有多重要。

```
時間  →
sensor ████████████████████████████████  (300 ms，無法被打斷)
button                                  ▌ ← 這時才被處理
       ↑ 使用者在這裡按下
       |←────── 延遲約 300 ms ──────→|
```

要改善，只能把慢的工作**手動切成很多小步驟**，改寫成狀態機，每次只做一小步就返回。這可行，但程式會變得破碎難讀，而且每新增一件工作，都要重新檢查所有工作的時序。

## RTOS（即時作業系統）

### 結構

```c
void led_task(void *arg)    { while (1) { toggle_led();   vTaskDelay(500); } }
void sensor_task(void *arg) { while (1) { read_sensor();  vTaskDelay(1000); } }
void button_task(void *arg) { while (1) { wait_button();  handle_press(); } }
```

每件工作是一個**任務（task）**：有自己的無窮迴圈、自己的堆疊，寫起來就像「整顆 CPU 只屬於我」。
由 RTOS 的**排程器（scheduler）在執行期間**決定現在該跑哪一個任務。

### 搶佔式排程

FreeRTOS 的規則很簡單：

> **永遠執行「就緒（Ready）」任務中優先權最高的那一個。**

當高優先權任務變成就緒（例如等待的時間到了、等的資料來了），排程器會**立刻暫停**正在執行的低優先權任務，把 CPU 交給高優先權任務。這稱為**搶佔（preemption）**。被搶佔的任務不需要配合，甚至不會知道自己被暫停過。

```
時間  →
button (高)              ██                    ← 立刻執行
sensor (低) █████████████  ██████████████████  ← 被暫停，之後從中斷處繼續
            ↑            ↑
            |            使用者按下按鈕
            sensor 開始運算
```

### 任務的狀態

```
              ┌──────────┐   被排程器選中   ┌──────────┐
   建立 ────▶ │  Ready   │ ───────────────▶ │ Running  │
              │  就緒    │ ◀─────────────── │  執行中  │
              └──────────┘     被搶佔       └──────────┘
                   ▲                             │
                   │ 等的事件發生／時間到        │ 呼叫會等待的 API
                   │                             ▼ (vTaskDelay、xQueueReceive…)
              ┌─────────────────────────────────────┐
              │            Blocked 阻塞             │
              └─────────────────────────────────────┘
```

**Blocked 是 RTOS 的精髓**：任務在等待時完全不佔 CPU。
超級迴圈的「等待」是不斷地問「好了沒？」（輪詢）；RTOS 的等待是「好了叫我」。

當所有任務都在 Blocked，系統會執行內建的 **idle task**，可藉此進入省電模式。

### 上下文切換與 tick

- **上下文切換（context switch）**：排程器把目前任務的 CPU 暫存器存進它的堆疊，再載入下一個任務的暫存器。在 ESP32 上約數微秒到十餘微秒。
- **Tick**：一個週期性的計時器中斷（ESP-IDF 預設 100 Hz，即 10 ms）。每次 tick，排程器檢查有沒有任務的延遲到期，並讓同優先權的任務輪流執行（time slicing）。`vTaskDelay()` 的時間解析度就是一個 tick。

## 代價：RTOS 不是免費的

| 代價 | 說明 |
|---|---|
| 記憶體 | 每個任務都需要自己的堆疊（ESP32 上常見 2～4 KB），加上核心本身的資料結構 |
| CPU | 上下文切換、tick 中斷都要花時間 |
| **並行錯誤** | 任務可能在任何兩行程式之間被搶佔，共用資料若沒有保護就會出錯（競爭條件）。保護不當又會產生死結、優先權反轉 |
| 除錯難度 | 與時序相關的錯誤往往難以重現 |
| 堆疊大小 | 每個任務的堆疊要配多大必須自己估計，配太小會溢位當機 |

超級迴圈最大的優點，正是**沒有這些問題**：只有一條執行路徑，除了 ISR 之外不會有人打斷你，程式行為完全可預測。

## 比較表

| 面向 | 超級迴圈 | FreeRTOS |
|---|---|---|
| 誰決定執行順序 | 程式設計師（撰寫時固定） | 排程器（執行時依優先權決定） |
| 排程方式 | 合作式：工作必須自己返回 | 搶佔式：高優先權可隨時打斷低優先權 |
| 最壞反應時間 | 其他所有工作時間的總和 | 接近固定（上下文切換時間），與低優先權工作無關 |
| 等待的方式 | 輪詢（忙碌等待或檢查旗標） | 阻塞（不佔 CPU，事件發生時被喚醒） |
| 耗時工作的寫法 | 必須手動拆成狀態機 | 直接照順序寫，排程器會處理 |
| 新增一件工作 | 需重新檢視整體時序 | 新增一個任務，對既有任務影響小 |
| 共用資料 | 幾乎不用保護（只需注意 ISR） | 必須用 mutex／queue 等機制保護 |
| RAM 用量 | 低（單一堆疊） | 較高（每個任務一個堆疊） |
| 時序可預測性 | 高，容易以推理驗證 | 需分析優先權與阻塞關係 |
| 省電 | 需自行設計 | idle task 可自動進入低功耗 |
| 學習與除錯難度 | 低 | 較高 |

## 該選哪一個？

**適合超級迴圈：**

- 工作少、彼此時序關係單純
- 每件工作都很短（或容易拆成短步驟）
- RAM 極少的微控制器（幾 KB 以下）
- 需要以推理嚴格證明時序的簡單系統

**適合 RTOS：**

- 有些工作很耗時，同時又有工作需要快速反應
- 工作的重要性差異大（需要優先權）
- 使用網路、藍牙、檔案系統等本身就需要多工的協定堆疊
- 多人協作開發，希望各模組能獨立撰寫與測試
- 系統會持續擴充

在 ESP32 上，這個選擇其實已經替你做好了：Wi-Fi 與藍牙協定堆疊都建立在 FreeRTOS 之上，系統一開機 FreeRTOS 就在執行。
所以真正的問題是——**你要不要善用它**。學完這份教程，你會有能力判斷。

## 名詞對照

| 中文 | 英文 | 說明 |
|---|---|---|
| 任務 | task | RTOS 中獨立執行的單位，又稱執行緒 |
| 排程器 | scheduler | 決定哪個任務執行的核心元件 |
| 搶佔 | preemption | 強制暫停目前任務，改執行更高優先權的任務 |
| 阻塞 | blocked | 任務等待事件或時間、不佔 CPU 的狀態 |
| 上下文切換 | context switch | 儲存一個任務的狀態並載入另一個 |
| 佇列 | queue | 任務之間傳遞資料的先進先出緩衝區 |
| 互斥鎖 | mutex | 確保一次只有一個任務存取共用資源 |
| 號誌 | semaphore | 用於同步或計數的訊號機制 |
| 競爭條件 | race condition | 結果取決於任務執行時序的錯誤 |
| 臨界區段 | critical section | 不可被打斷的一段程式 |
| 中斷服務程式 | ISR | 硬體中斷發生時執行的函式 |
| 抖動 | jitter | 週期性動作實際發生時間的變動量 |
